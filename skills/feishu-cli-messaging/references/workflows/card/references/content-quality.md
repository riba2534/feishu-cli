# 卡片内容真实性与发送前审查

卡片不是把 JSON 拼对就结束。它通常会触发判断、审批或行动，所以“内容从哪里来、哪些还
不知道、按钮是否真的可用”与结构合法性同样重要。

## 1. 先做事实账本

生成卡片前，把输入拆成四类；不要用常识替用户补齐业务事实。

| 类别 | 处理方式 | 示例 |
|---|---|---|
| 用户明确给出的事实 | 原样保留语义，可压缩措辞 | 状态、影响范围、发生时间 |
| 可从已授权数据源读取的事实 | 读取后注明来源与时间 | 监控值、工单状态、负责人 |
| 可安全推导的表达 | 标成“推断”或改为中性措辞 | “错误率上升，可能影响登录” |
| 缺失信息 | 草稿中保留明确 TODO；发送前补齐或删掉相关模块 | 监控 URL、审批人、样本量 |

禁止：

- 编造负责人、百分比、时间、URL、用户 ID、图片 `img_key` 或数据源；
- 把“未知”改写成确定结论；
- 用 `example.com`、`ou_xxx`、`img_v2_xxx` 等示例值生成发送候选；
- 为了让卡片“更完整”而增加没有事实依据的图表或指标。

## 2. 草稿与发送候选是两种状态

### 草稿

草稿允许 `__MONITOR_URL__`、`TODO_OWNER_ID` 这类机器可查的占位符，但要同时给用户一份
未决项清单。草稿检查使用：

```bash
python3 skills/feishu-cli-messaging/references/workflows/card/scripts/lint_card.py \
  --allow-placeholders /tmp/card-draft.json
```

草稿只能用于评审，不得发送。占位按钮如果没有真实目标，优先整个删除；只有用户确实计划
补齐行动入口时才保留 TODO。

### 发送候选

发送候选不得带占位符、示例 ID 或示例 URL：

```bash
python3 skills/feishu-cli-messaging/references/workflows/card/scripts/lint_card.py \
  --strict /tmp/card-final.json
```

离线检查通过仍不等于服务端一定接收。它只覆盖项目内可以稳定判断的错误；正式发送前还要
在测试会话或卡片搭建工具预览 PC 与移动端，尤其是表单、回调、图表和复杂嵌套。

## 3. 内容结构

按“结论 → 证据 → 行动 → 来源”组织，而不是按用户提供素材的先后顺序照抄。

1. **首屏结论**：标题说明发生了什么；第一段回答状态、影响或结论。
2. **关键证据**：只展示支持结论的 2–4 个指标或事实。
3. **必要详情**：列表、表格或图表；长内容进入折叠面板。
4. **真实行动**：最多一个主动作，零到两个次动作。
5. **来源脚注**：数据源、统计窗口、更新时间；样本数据必须明确标注。

标题避免“通知”“数据看板”这类空泛文案。优先写“支付成功率降至 96.2%”或“v2.4.0
已发布”。

## 4. 按钮和交互必须可兑现

- 只有真实 URL 才放 `open_url` 按钮。
- 只有事件消费端已经准备好时才放 `callback`；回传 `value` 要能唯一识别动作和对象。
- 表单必须有 `form_action_type: "submit"` 的提交按钮，并确认服务端能处理表单回调。
- “忽略”“归档”“同意”这类会改变状态的动作，应有明确回调语义；高风险动作增加确认。
- 没有后端能力时，用正文说明下一步，不要画一个不能工作的按钮。

发送卡片与搭建交互处理器是两件事。`feishu-cli msg send` 能发送 Card JSON，不会自动实现
按钮回调逻辑。

## 5. 数据与图表

- 图表字段必须能在 `chart_spec.data.values` 中找到。
- 展示时间序列时写清时区、时间窗口和采样粒度。
- 对比值必须说明基线，例如“较昨日同一时段”。
- 表格列名使用用户语言，不暴露内部字段名；`rows` 的 key 与 `columns.name` 一致。
- 数据少于三个点或图形不会提升理解时，改用数字或短表格。
- 样本、估算和推断必须显式标记，不能伪装成线上实时数据。

## 6. 可读性与无障碍

- 颜色只强化语义，不能成为唯一信号；同时写“成功 / 警告 / 失败”等文字。
- 图片提供有意义的 `alt`，不要写“图片”“截图”。
- 一段只承载一个观点；移动端首屏应能看到结论而不是大段背景。
- 正文保持正常字号；`notation` 只用于来源与辅助说明。
- 折叠面板标题条保持白色或浅色 surface；不要把语义色铺满横条，应改用标题文字、图标或
  细边框上色，避免次级导航抢过主标题。
- 深色模式下使用 `config.style.color` 时同时提供 `light_mode` 与 `dark_mode`。
- emoji 用于导航，不要每行一个；避免依赖生僻图标表达关键状态。

## 7. 发送前双重审查

### 内容审查

- [ ] 每个数字、名字、ID、URL 都有来源
- [ ] 推断、样本与未知项已清楚标识
- [ ] 没有未替换占位符或示例值
- [ ] 主结论与证据一致
- [ ] 按钮和表单有真实可用的后端
- [ ] 时间窗口、来源、更新时间齐全

### 视觉审查

- [ ] 首屏能回答“发生了什么、是否需要我处理”
- [ ] 只有一个主要视觉焦点
- [ ] 颜色、字号、间距形成清楚层级
- [ ] 折叠标题条为白色/浅色，语义色用于字体、图标或细边框而非整条背景
- [ ] 表格和图表在窄屏仍可读
- [ ] 次要信息已折叠或删除
- [ ] PC、移动端、浅色与深色模式已按风险检查

不要给审查结果编造一个“专业分数”。直接列出阻断发送的问题、非阻断建议和已确认项。
